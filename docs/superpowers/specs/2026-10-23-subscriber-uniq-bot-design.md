# Бот-уникализатор для подписчиков: дизайн

Дата: 2026-10-23. Статус: на согласовании у владельца.

## 1. Цель и рамки

Бесплатный Telegram-бот для подписчиков канала владельца: подписчик присылает видео и получает одну
уникализированную копию. Образец по смыслу: @parfentev_uniq_bot («Обработка Reels до 200 МБ»), но без оплаты,
без Web App и без выбора режима. Заодно бот собирает базу пользователей для рассылок и аналитики.

Решения владельца (2026-10-23):

- доступ только подписчикам канала владельца;
- одно видео → одна копия, режим один, без выбора;
- бот живёт на текущей VPS рядом с ботом рилсов (2 vCPU, 3.9 ГБ, без swap);
- лимита в сутки нет, у человека одновременно только один заказ;
- движок: Hostlife22/video-uniquifier (MIT) с его пресетом `instagram_reels`, усиленным (раздел 4);
- база пользователей, выгрузка, рассылки входят в этот этап.

Вне рамок: Web App, оплата, несколько режимов и копий, ссылки на ролики (только файлы), субтитры,
наш гейт PDQ + Chromaprint из Уникализатора, сегменты аудитории для рассылок, продолжение прерванной рассылки.

## 2. Сценарии подписчика

### 2.1 Старт и подписка

- `/start [метка]`: бот создаёт или обновляет пользователя (раздел 5), затем проверяет подписку.
- Не подписан: текст «Бот бесплатный для подписчиков канала …» и инлайн-кнопки **Подписаться** (ссылка на
  канал) и **Я подписался** (повторная проверка, ответ правкой того же сообщения).
- Подписан: короткая инструкция: «Пришли видео до 200 МБ и до 3 минут, верну уникальную копию файлом».
- Проверка подписки: `getChatMember(CHANNEL_ID, user_id)`. Подписан, если статус `creator`, `administrator`,
  `member` или `restricted` с `is_member = true`. `left` и `kicked` значат «не подписан».
- Подписка проверяется на `/start`, на кнопке **Я подписался** и на каждом присланном видео. Результат и время
  проверки пишутся в `users`.
- Если сам вызов Telegram упал (например, бот не админ канала): пользователю «Временная ошибка, попробуй через
  пару минут», админам уведомление не чаще раза в 10 минут. Пропускать без проверки нельзя.

### 2.2 Приём видео

Принимаются сообщения с `video` и с `document`, у которого MIME `video/*`. Всё остальное (кружки, GIF, фото,
текст) получает подсказку «Пришли обычное видео файлом или как видео».

Проверки по порядку, первая сработавшая отвечает пользователю и заказ не создаётся:

1. подписка (2.1);
2. размер > `MAX_FILE_MB` (по умолчанию 200): «Файл больше 200 МБ»;
3. длительность из метаданных Telegram > `MAX_DURATION_SEC` (по умолчанию 180): «Видео длиннее 3 минут».
   Для документов длительности в сообщении нет, её проверяет ffprobe при обработке (2.3);
4. у пользователя есть заказ `queued` или `processing`: «У тебя уже есть видео в работе, дождись результата».

Иначе создаётся заказ `queued` с `file_id`, ответ: «Принял! Ты в очереди: N-й. Результат пришлю сюда».
N = число заказов `queued` с меньшим id + 1, плюс 1, если сейчас что-то обрабатывается. id этого сообщения
сохраняется в заказ, дальше бот его правит.

### 2.3 Обработка

Один воркер, строго один заказ за раз, FIFO по id.

1. Заказ → `processing`, статус-сообщение → «Обрабатываю…».
2. `getFile` через локальный сервер Bot API (раздел 7) отдаёт путь к файлу на общем томе; файл переносится в
   `data/work/<order_id>/input.<ext>`, копия на сервере API удаляется.
3. ffprobe: есть видеопоток, длительность ≤ `MAX_DURATION_SEC`. Иначе `failed` с понятным текстом.
4. Подготовка входа в `clean.mkv`: только первый видеопоток (не обложка) и первый аудиопоток, если он есть;
   без субтитров, служебных дорожек, глав и метаданных. Обычно это копирование потоков без перекодирования.
   Если кадр записан с пометкой поворота (типично для телефона) или видео в HDR (PQ или HLG, типично для
   iPhone), видео перекодируется: поворот применяется, HDR переводится в SDR BT.709 тем же фильтром, что
   `video.tonemap_sdr` движка (hable, peak 1000), libx264 CRF 14 `veryfast`. Так движок всегда получает
   вертикально стоящий SDR-кадр с одной аудиодорожкой: его preflight отклоняет HDR без тонмаппинга и
   служебные дорожки в MP4.
5. Генерируется профиль заказа (раздел 4) в `data/work/<order_id>/profile.yaml`.
6. Запуск отдельным процессом:
   `nice -n 10 video-uniq run clean.mkv --profile profile.yaml --out output.mp4 --work-dir data/work/<order_id>/tmp --no-qa --no-progress`
   с таймаутом `RENDER_TIMEOUT_SEC` (по умолчанию 900). Код возврата ≠ 0 или таймаут → `failed`.
7. Успех: `sendDocument` с `output.mp4` под именем `uniq_<8 символов>.mp4` и подписью «Готово ✅ Можно
   выкладывать». Статус-сообщение → «Готово ✅». `users.videos_done += 1`, заказ → `done`.
8. В конце всегда удаляется `data/work/<order_id>/`.

Ошибка: пользователю «Не получилось обработать это видео, пришли другой файл», заказ `failed` с текстом причины
и хвостом stderr (≤ 2000 символов), админам уведомление (id заказа, пользователь, причина).

Перезапуск бота: заказы `processing` возвращаются в `queued` и обрабатываются заново. Входной файл берётся
снова по `file_id`. При старте удаляются каталоги `data/work/*`, которым не соответствует активный заказ.

## 3. Админ-функции

Админы: Telegram ID из `ADMIN_IDS`. Для остальных команды ниже молчат.

- `/stats`: пользователей всего; новых за сутки и за 7 дней; активных за 7 дней (`last_seen`); подписанных по
  последней проверке; заблокировавших бота; видео `done` за сутки и всего; `failed` за сутки; длина очереди.
- `/users`: файл `users_<дата>.csv` (UTF-8 с BOM, разделитель `;`, чтобы Excel открывал без настройки) со
  всеми полями `users`.
- `/broadcast`:
  1. бот: «Пришли пост для рассылки» (ждёт следующее сообщение админа, `/cancel` отменяет);
  2. админ присылает любое сообщение (текст, фото, видео, с инлайн-кнопками-ссылками или без);
  3. бот копирует его админу как превью и спрашивает «Отправить N пользователям?» с кнопками **Отправить** /
     **Отмена**. N = пользователи с `blocked = false`;
  4. после **Отправить** рассылка идёт в фоне: `copyMessage` из чата админа каждому адресату, не быстрее
     20 сообщений в секунду. `RetryAfter` → пауза на указанное время и повтор того же адресата.
     `Forbidden` → `users.blocked = true`. Прочие ошибки считаются как неудачи;
  5. каждые 100 адресатов бот правит своё сообщение с прогрессом, в конце присылает отчёт: доставлено,
     заблокировали, ошибки.

  Одновременно идёт одна рассылка. Рассылка не останавливает обработку видео. **Отмена** на шаге 3 даёт
  `cancelled`; запущенную рассылку остановить нельзя. Прерванная перезапуском рассылка не продолжается:
  при старте бота она помечается `interrupted` с числом уже отправленных.
- Уведомления админам: упавший заказ; ошибка проверки подписки (2.1).

Для всех: `/privacy` выводит абзац о том, что хранится (поля `users`), зачем (доступ, статистика, рассылки),
и что файлы видео удаляются сразу после обработки.

## 4. Профиль уникализации

Основа: пресет `instagram_reels.yaml` из пакета video-uniquifier. Бот на каждый заказ пишет профиль с теми же
преобразованиями движка, но со значениями, случайно выбранными из диапазонов в `config/uniq.yaml`. Так два
пользователя с одним и тем же роликом получают разные копии.

| Преобразование | В пресете | Значение в заказе (стартовые диапазоны) |
|---|---|---|
| `video.fit_aspect` | 9:16, `pad_blur`, σ 25, `allow_upscale` | без изменений (размытый фон виден только у невертикальных видео) |
| `video.crop_resize` | `max_strength` 0.02 | `max_strength` 0.10 (верхняя граница схемы движка); фиксированный `rng_seed` убирается |
| `video.color_eq` | 0.01 / 1.018 / 0.996 / 1.025 | brightness U(−0.02, 0.02), contrast U(1.01, 1.04), gamma U(0.98, 1.02), saturation U(0.97, 1.06) |
| `video.noise` | 3 | целое из {4, 5} |
| `video.speed` | нет | `rate = r` |
| `audio.pitch_tempo` | pitch 1.0008, tempo 1.0 | `pitch = r`, `tempo = r` |
| `audio.eq` | по умолчанию | без изменений |
| `audio.loudnorm` | −16 LUFS | без изменений |

`r` выбирается из {0.96, 0.97, 1.03, 1.04}, но только среди тех, при которых итоговая длительность
`duration / r` не больше 180 с (лимит Reels). Если таких нет, берётся наибольший `r`. Видео, темп и тон меняются вместе («магнитофонный» сдвиг без
растяжения звука), поэтому preflight движка (`video.speed.rate == audio.pitch_tempo.tempo`) проходит.
`video.speed` ставится последним из видеопреобразований (порядок из `docs/transform_reference.md` движка:
геометрия → цвет → шум → время). `seed_strategy` остаётся по умолчанию (`per_run`).

Кодирование, метаданные, CRF 18, AAC остаются как в движке. Совместимость итогового профиля проверяется на
этапе реализации через `video-uniq run --dry-run`.

Диапазоны стартовые. Окончательные подбираются на приёмке (раздел 9) и меняются правкой `config/uniq.yaml`
без изменения кода.

## 5. Данные (SQLite, `data/bot.db`)

`users`:

| Поле | Смысл |
|---|---|
| `tg_id` (PK) | Telegram ID |
| `username`, `first_name`, `last_name`, `language_code`, `is_premium` | из последнего апдейта пользователя, обновляются при каждом сообщении и нажатии кнопки |
| `source` | метка из первого `/start <метка>` (`[A-Za-z0-9_-]{1,64}`), больше не перезаписывается; `NULL` без метки |
| `first_seen`, `last_seen` | UTC |
| `is_subscribed`, `subscription_checked_at` | результат последней проверки (2.1); `NULL` до первой |
| `videos_done` | число заказов `done` |
| `blocked`, `blocked_at` | бот заблокирован пользователем: из апдейта `my_chat_member` (`kicked` → true, `member` → false) и из `Forbidden` при отправке |

`orders`: `id`, `tg_id`, `file_id`, `file_size`, `duration` (может быть `NULL`), `status`
(`queued` / `processing` / `done` / `failed`), `status_message_id`, `error`, `created_at`, `started_at`,
`finished_at`, `params_json` (выбранные значения профиля, для разбора жалоб на качество).

`broadcasts`: `id`, `admin_id`, `source_chat_id`, `source_message_id`, `total`, `sent`, `blocked`, `failed`,
`status` (`running` / `done` / `cancelled` / `interrupted`), `created_at`, `finished_at`.

Видеофайлы в базе не хранятся.

## 6. Устройство кода

Python 3.12, aiogram 3, SQLAlchemy 2 async + aiosqlite, pydantic-settings, pytest. Модули:

- `config` — настройки из `.env` и `config/uniq.yaml`;
- `db` — модели и запросы;
- `access` — проверка подписки;
- `intake` — приём видео и проверки 2.2;
- `worker` — очередь и обработка 2.3;
- `profile` — генератор профиля из раздела 4 (чистая функция от `random.Random`, тестируется без ffmpeg);
- `engine` — запуск `video-uniq` и ffprobe;
- `admin` — `/stats`, `/users`, `/broadcast`;
- `texts` — все тексты для пользователя в одном месте.

## 7. Развёртывание

На VPS отдельный каталог `/opt/uniqbot` и свой `docker-compose.yml`, бот рилсов не затрагивается:

- `bot-api`: официальный сервер Telegram Bot API в режиме `--local` (образ `aiogram/telegram-bot-api`
  с фиксированным тегом). Снимает лимиты 20 МБ на скачивание и 50 МБ на отправку. Данные на томе, общем с `bot`.
  `mem_limit` 256 МБ;
- `bot`: `python:3.12-slim` + `ffmpeg` из пакетов Debian (как в Dockerfile движка) + video-uniquifier
  `git+https://github.com/Hostlife22/video-uniquifier@e9138dd` (v2.1.2) + наш пакет. Без OpenCV, поэтому
  проверка водяных знаков движка не включается. Работает не от root, а под uid/gid 101: под ними сервер
Bot API пишет файлы на общий том, и бот должен их читать и удалять. `cpu_shares` 256 (у бота рилсов по
  умолчанию 1024: при одновременной работе его рендер получает процессор первым), `mem_limit` 1536 МБ;
- `data/` (база и рабочие каталоги) и `.env` лежат вне каталога с кодом;
- одноразово: бот выходит из облачного Bot API (`logOut`) перед переходом на локальный сервер.

`.env`: `BOT_TOKEN`, `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `CHANNEL_ID`, `CHANNEL_URL`, `ADMIN_IDS`,
`MAX_FILE_MB`, `MAX_DURATION_SEC`, `RENDER_TIMEOUT_SEC`.

В репозитории `NOTICE` с текстом MIT video-uniquifier.

## 8. Нужно от владельца

- новый бот в @BotFather (токен только в `.env` на сервере);
- `api_id` и `api_hash` с my.telegram.org (бесплатно, нужны локальному серверу Bot API);
- канал и добавление бота в его администраторы без прав на публикацию;
- явное «да» на деплой и SSH на VPS.

## 9. Проверка и приёмка

- Юнит-тесты: правила подписки по статусам; проверки приёма 2.2 и их порядок; позиция в очереди;
  переходы заказа и возврат `processing` → `queued` при старте; генератор профиля (значения в диапазонах,
  `rate == tempo == pitch`, порядок преобразований, нет `rng_seed`); обновление `users` и первая метка
  `source`; CSV (BOM, `;`, все поля); рассылка с поддельным ботом (`RetryAfter`, `Forbidden`, прогресс, отчёт).
- Интеграционные тесты (медленные, локально и в Docker): настоящий `video-uniq run` с профилем заказа на
  синтетических роликах по 2 с (`testsrc` + `sine`): вертикальный, горизонтальный, без звука, HLG HDR,
  с пометкой поворота, MOV с дорожкой таймкода и PCM-звуком. Выход 1080×1920 SDR, декодируется,
  длительность изменилась в `1/r` раз.
- Подбор диапазонов: 5–10 роликов владельца через бота локально; `video-uniq qa` (pHash, Chromaprint против
  исходника) и просмотр с прослушиванием владельцем. Итог фиксируется в `config/uniq.yaml`.
- Приёмка на VPS: два аккаунта (подписанный и нет), видео как файл и как видео, файл больше 20 МБ, второй
  заказ во время первого, `/stats`, `/users`, `/broadcast` на базу из своих аккаунтов, блокировка бота
  одним аккаунтом и проверка `blocked`. Бот рилсов во время теста продолжает работать.
